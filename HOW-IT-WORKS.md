# Как устроен этот проект

Документ для тех, кто только начинает программировать. Предполагается, что
ты уже знаешь:

- что такое **файл** (именованный набор байтов на диске);
- что такое **процесс** (запущенная программа, которой ОС выделила память и
  процессорное время);
- что такое **ОС** (программа, которая управляет железом, файлами и процессами);
- что такое **IP-адрес** (номер компьютера в сети, по которому к нему
  подключаются);
- что такое **HTML** и что его показывает браузер.

Дальше — как из этого складывается вся игра: от кода в редакторе до сайта,
который открывается у любого человека в интернете.

## Схема 1. Вся система целиком

В проекте участвуют три компьютера и несколько программ (процессов) на них.

```text
 (А) Сервер разработки              (Б) GitHub                 (В) Компьютер игрока
 IP 46.226.165.215                  серверы компании GitHub    любой, где есть браузер
+---------------------------+      +----------------------+   +----------------------+
| папка с кодом:            |      | репозиторий          |   | процесс: браузер     |
| ~/ai-projects/canvas-game | ---> | roman123123su/       |   | (Chrome, Firefox...) |
|   index.html, game.js     | git  |   canvas-game        |   |                      |
|                           | push |                      |   | показывает игру      |
| процесс: Caddy            |      | GitHub Actions:      |   +----------+-----------+
| (веб-сервер, порт 443)    | <--- | временная машина     |              |
|                           | SSH  | собирает и отправляет|              |
| папка с сайтом:           |      | файлы на сервер      |              |
| codex-vibe-data/live/     |      +----------------------+              |
|   canvas-game/            |                                            |
+-------------+-------------+                                            |
              ^                  HTTPS-запрос по IP 46.226.165.215       |
              +----------------------------------------------------------+
                    ответ: содержимое файлов index.html и game.js
```

Важно заметить:

- Код правится и сайт работает на **одном и том же** сервере (А). Но код
  попадает в папку сайта не напрямую, а через GitHub (Б). Так у каждой
  версии сайта есть коммит, и видно, что и когда выкладывалось.
- Игра **выполняется на компьютере игрока** (В), а не на сервере. Сервер
  только отдаёт два файла. Весь JavaScript работает внутри процесса
  браузера у игрока.

## Схема 2. Что происходит при открытии сайта

Игрок вводит в браузере `https://canvas-game.apps.botops.ru`.

```text
 Браузер игрока                                   Сервер 46.226.165.215
 --------------                                   ---------------------

 1. DNS-запрос:
    "какой IP у canvas-game.apps.botops.ru?"
    ответ DNS-сервера: 46.226.165.215

 2. TCP-соединение на 46.226.165.215, порт 443 ---> ОС сервера передаёт
                                                    соединение процессу,
                                                    который слушает порт 443:
                                                    это Caddy

 3. TLS (буква S в HTTPS): шифрование   <-------->  Caddy показывает
    браузер проверяет сертификат                    сертификат для домена

 4. HTTP-запрос:  GET /            ------------->   Caddy смотрит на имя домена,
                                                    находит папку
                                                    live/canvas-game/ и читает
                                                    файл index.html
                  <-------------   ответ: текст index.html

 5. Браузер разбирает HTML, видит
    <script src="game.js">
    и делает второй запрос:
                  GET /game.js     ------------->   читает файл game.js
                  <-------------   ответ: текст game.js

 6. Браузер выполняет game.js.
    Дальше сервер больше не нужен:
    игра работает внутри браузера.
```

Пояснения:

- **DNS** — система, которая переводит имя сайта в IP-адрес. Людям удобно
  имя, а сетевым соединениям нужен IP.
- **Порт** — номер внутри одного IP, по которому ОС понимает, какому процессу
  отдать входящее соединение. 443 — стандартный порт для HTTPS.
- **Caddy** — программа-веб-сервер. Её процесс постоянно запущен на сервере,
  принимает HTTP-запросы и в ответ отдаёт файлы с диска. Один Caddy
  обслуживает много сайтов: по имени домена в запросе он выбирает нужную папку.

## Схема 3. Файлы игры и их связь

Вся игра — это два файла.

```text
index.html  (26 строк)
+------------------------------------------------------------+
| <head>                                                     |
|   <style> ... </style>   CSS: тёмный фон, холст по центру  |
| </head>                                                    |
| <body>                                                     |
|   <canvas id="gameCanvas" width="600" height="400">        |
|        ^  прямоугольник 600x400 пикселей,                  |
|        |  в котором можно рисовать из JavaScript           |
|        |                                                   |
|   <script src="game.js"></script>                          |
|        |  "загрузи и выполни этот файл"                    |
+--------|---------------------------------------------------+
         |
         v
game.js  (~1000 строк)
+------------------------------------------------------------+
| const canvas = document.getElementById('gameCanvas');      |
|        ^ находит тот самый <canvas> по id                  |
| const ctx = canvas.getContext('2d');                       |
|        ^ ctx - объект с командами рисования:               |
|          fillRect (прямоугольник), arc (круг),             |
|          fillText (текст) и т.д.                           |
| ...                                                        |
| вся логика игры                                            |
+------------------------------------------------------------+
```

Разница с обычной HTML-страницей:

- В обычной странице содержимое (текст, картинки, кнопки) записано прямо
  в HTML, и браузер сам его рисует.
- Здесь в HTML только пустой `<canvas>`. Всё, что видно на экране — игрок,
  враги, монеты, текст меню — рисует `game.js` командами `ctx.*`, пиксель
  за пикселем, заново каждый кадр.

## Схема 4. Карта файла game.js

Файл читается сверху вниз. Номера строк примерные.

```text
строки     что там
--------   ------------------------------------------------------------
1-2        canvas и ctx - доступ к холсту
4-44       СОСТОЯНИЕ ИГРЫ - переменные, где хранится "всё, что сейчас есть":
             player      позиция x/y, скорость, жизни (hp)
             coin        где лежит монета
             levels      массив из 5 уровней: Лес, Пустыня, Снега,
                         Вулкан, Космос (параметры врагов, сколько монет)
             score, levelIndex, coinsCollected   счёт и прогресс
             phase       текущая фаза: 'menu', 'transition', 'playing',
                         'gameover', 'victory'  (см. схему 7)
             enemies, bullets, particles, obstacles   массивы объектов
             boss        босс на последнем уровне (или null)
48-101     ЗВУК - playCoinSound, playShootSound... (Web Audio API)
103-316    ВСПОМОГАТЕЛЬНЫЕ ФУНКЦИИ:
             spawnCoin, spawnEnemy, spawnBoss   создать объект
             startLevel, resetGame, finishLevel  переключение уровней
             shoot            создать пулю
             resolveCircle    не дать пройти сквозь препятствие
317-346    ВВОД - обработчики клавиатуры (keydown / keyup)
350-558    update(dt)  - ЛОГИКА одного шага игры
560-570    updateParticles - искры от взрывов
572-980    render() и draw*  - РИСОВАНИЕ кадра
983-993    loop()  - ИГРОВОЙ ЦИКЛ, связывает update и render
```

Главная идея: **данные** (переменные состояния) отделены от **логики**
(update меняет данные) и от **рисования** (render только читает данные и
рисует). Если нужно поменять, как выглядит враг — правь `render`/`draw*`.
Если как он двигается — правь `update`.

## Схема 5. Игровой цикл

Игра — это не страница, которая один раз нарисовалась. Это функция,
которая перерисовывает всё примерно **60 раз в секунду** (с частотой
обновления монитора).

```text
      Клавиатура
          |
          |  браузер вызывает обработчики событий
          v
  +----------------------+
  | keydown / keyup      |   keys['ArrowRight'] = true / false
  | (строки 317-346)     |   объект keys запоминает, какие клавиши
  +----------+-----------+   сейчас зажаты
             |
             |  update() читает keys
             v
  +-------------------------------------------------------------+
  |  loop(timestamp)                           (строки 983-991) |
  |                                                             |
  |   dt = сколько секунд прошло с прошлого кадра (~0.016)      |
  |                                                             |
  |   1. update(dt)   изменить состояние:                       |
  |        - сдвинуть игрока по нажатым клавишам                |
  |        - сдвинуть врагов и пули                             |
  |        - проверить столкновения                             |
  |        - начислить очки, отнять жизни, сменить уровень      |
  |                                                             |
  |   2. render()     нарисовать состояние:                     |
  |        - залить фон                                         |
  |        - нарисовать препятствия, монету, врагов, игрока     |
  |        - нарисовать счёт и жизни (HUD)                      |
  |                                                             |
  |   3. requestAnimationFrame(loop)                            |
  |        "браузер, вызови loop ещё раз перед следующим        |
  |         обновлением экрана"                                 |
  +-------------------------------------------------------------+
        ^                                                |
        |    примерно через 1/60 секунды браузер         |
        +------------- снова вызывает loop --------------+
```

Зачем нужен `dt`. Компьютеры разные: у одного 60 кадров в секунду, у
другого 144. Если сдвигать игрока на фиксированное число пикселей за кадр,
на быстром мониторе он бегал бы в 2 раза быстрее. Поэтому скорость задана
в пикселях **в секунду** (`player.speed = 250`), а сдвиг за кадр считается
как `скорость * dt`. Тогда за одну секунду игрок проходит 250 пикселей на
любом компьютере.

## Схема 6. Один кадр на примере

Игрок держит стрелку вправо. Прошло 0.016 секунды с прошлого кадра.

```text
 состояние ДО кадра:   player.x = 280,  keys['ArrowRight'] = true

 update(0.016):
   dx = +1                             (зажата стрелка вправо)
   player.x += 1 * 250 * 0.016         -> player.x = 284
   resolveCircle(player)               если врезался в препятствие -
                                       вытолкнуть обратно
   расстояние до монеты < суммы радиусов?
     да  -> score + 1, звук, новая монета в случайном месте
            хватает монет на уровень? -> finishLevel()
     нет -> ничего
   для каждого врага: сдвинуть к игроку;
     коснулся игрока? -> player.hp - 1

 render():
   стереть холст и залить фоном уровня
   нарисовать квадрат игрока в точке x = 284
   нарисовать всё остальное и счёт

 состояние ПОСЛЕ кадра: player.x = 284
 на экране игрок сдвинулся на 4 пикселя вправо
```

60 таких кадров в секунду глаз воспринимает как плавное движение.

## Схема 7. Фазы игры

Переменная `phase` определяет, что сейчас делают `update` и `render`.

```text
            загрузка страницы
                   |
                   v
             +-----------+
             |  'menu'   |  экран с управлением
             +-----+-----+
                   | Enter или Пробел -> resetGame() -> startLevel(0)
                   v
          +----------------+
  +-----> | 'transition'   |  заставка "Уровень N", 2 секунды
  |       +-------+--------+  (Enter - пропустить)
  |               | таймер закончился
  |               v
  |       +----------------+
  |       |  'playing'     |  основная игра: update двигает всё
  |       +--+-----+----+--+
  |          |     |    |
  | собраны  |     |    | hp = 0
  | монеты   |     |    v
  | уровня   |     |  +-------------+
  +----------+     |  | 'gameover'  |
startLevel(N+1)    |  +-------------+
                   |
                   | побеждён босс на последнем уровне
                   v
             +-------------+
             | 'victory'   |
             +-------------+

 Клавиша R в любой фазе -> resetGame() -> снова уровень 1.
```

## Схема 8. Git: от правки до GitHub

**Git** — программа, которая хранит историю изменений файлов в папке.
**GitHub** — сайт, где хранится копия этой истории (удалённый репозиторий).

```text
  рабочая папка              индекс (staging)          локальная история
  (файлы на диске)                                      (папка .git)
 +----------------+  git add  +----------------+  git  +----------------+
 | game.js        | --------> | что войдёт в   | ----> | коммит 4ae5307 |
 | (изменён)      |           | следующий      | commit| коммит 7f6e6ab |
 +----------------+           | коммит         |       | ...            |
                              +----------------+       +-------+--------+
                                                               |
                                                               | git push
                                                               v
                                                      +------------------+
                                                      | GitHub           |
                                                      | roman123123su/   |
                                                      |   canvas-game    |
                                                      | ветка master     |
                                                      +------------------+
```

- **Коммит** — снимок всех файлов проекта в какой-то момент плюс описание.
  У каждого коммита есть уникальный идентификатор (хеш), например `4ae5307`.
- **Ветка** — имя, указывающее на последний коммит линии разработки.
  Здесь основная ветка называется `master`.
- `git log --oneline` показывает список коммитов.

## Схема 9. Автодеплой (GitHub Actions)

**Деплой** — выкладка новой версии на сервер. Здесь он происходит
автоматически после каждого `git push` в ветку `master`.

Инструкция для GitHub лежит в файле `.github/workflows/deploy.yml`.

```text
 git push в master
        |
        v
 GitHub видит новый коммит и читает .github/workflows/deploy.yml
        |
        v
 GitHub создаёт временную виртуальную машину (Ubuntu 24.04)
 и выполняет на ней шаги по порядку:
 +------------------------------------------------------------------+
 | 1. Check out      скачать код именно этого коммита               |
 | 2. Build          mkdir dist && cp index.html game.js dist/      |
 |                   (в dist/ только то, что нужно браузеру;        |
 |                    README и .git на сайт не попадают)            |
 | 3. Check          проверить, что dist/index.html существует      |
 | 4. SSH identity   достать из секретов GitHub SSH-ключ и адрес    |
 |                   сервера (секреты не видны в коде)              |
 | 5. Deploy         упаковать dist/ в архив tar.gz и отправить     |
 |                   по SSH на сервер командой "deploy <хеш>"       |
 +--------------------------------+---------------------------------+
                                  | SSH, архив с файлами
                                  v
 Сервер 46.226.165.215 (скрипт botops-static):
 +------------------------------------------------------------------+
 | 6. распаковать архив в новую папку artifacts/<id сборки>/        |
 | 7. проверить, что Caddy отдаёт из неё правильный index.html      |
 | 8. переключить live/canvas-game на новую папку                   |
 | 9. открыть https://canvas-game.apps.botops.ru и проверить ответ  |
 |    если проверка не прошла - вернуть прежнюю версию              |
 | 10. удалить старые сборки, оставить последние 5                  |
 +------------------------------------------------------------------+
        |
        v
 временная машина GitHub удаляется; сайт уже обновлён
```

Обычно весь путь занимает меньше минуты. Ход выполнения видно на GitHub
во вкладке **Actions**: зелёная галочка — сайт обновлён, красный крест —
ошибка (текст ошибки внутри упавшего шага; при ошибке сайт остаётся на
прежней версии).

**SSH** — протокол для защищённого подключения к другому компьютеру по сети.
Вместо пароля используется ключ. Ключ этого проекта на сервере разрешает
выполнить только одну команду — `deploy` для этого сайта. Получить с ним
доступ к командной строке сервера или к другим сайтам нельзя.

## Схема 10. Папки на сервере и откат

```text
/home/devuser/codex-vibe-data/
|
+-- artifacts/                       каждая сборка - отдельная папка,
|   +-- b20260925192140ef99ab1/      после создания не меняется
|   |     index.html  game.js
|   +-- b202609251923067f6e6ab/
|   |     index.html  game.js
|   +-- b202609251940144ae5307/      <-- id сборки: дата-время + хеш коммита
|         index.html  game.js
|
+-- live/
    +-- canvas-game  --> ../artifacts/b202609251940144ae5307
         ^
         символическая ссылка (symlink): особый файл, который
         указывает на другую папку. Caddy отдаёт файлы из
         live/canvas-game, а фактически читает их из той сборки,
         на которую указывает ссылка.
```

Почему так:

- **Выкладка без полусломанного состояния.** Новые файлы сначала целиком
  записываются в новую папку, и только потом ссылка переключается. ОС
  меняет ссылку одной операцией, поэтому игрок никогда не получит новый
  `index.html` вместе со старым `game.js`.
- **Мгновенный откат.** Старые сборки лежат рядом. Откат — это просто
  переключение ссылки на предыдущую папку, ничего не нужно собирать заново.

Посмотреть текущее состояние:

```bash
botops-static status canvas-game
```

## Что делать после изменения кода

1. Открой `index.html` в браузере и проверь игру локально. Сборки и
   установки зависимостей нет — браузер читает файлы прямо с диска.
   Если что-то не работает, открой консоль браузера (F12 → Console): там
   видны ошибки JavaScript с номером строки.
2. Закоммить и отправь:

   ```bash
   git status                        # какие файлы изменены
   git diff                          # что именно изменено
   git add .
   git commit -m "описание изменения"
   git push
   ```

3. Открой вкладку **Actions** на GitHub и дождись зелёной галочки.
4. Открой https://canvas-game.apps.botops.ru. Если видна старая версия —
   браузер мог взять файлы из своего кеша: обнови страницу с Ctrl+Shift+R.

## Если новая версия сломана

**Способ 1: быстрый откат на сервере** (сайт починится за секунды):

```bash
botops-static rollback canvas-game
```

Команда выполняется на сервере 46.226.165.215 (там же, где лежит папка с
кодом). Она переключает ссылку `live/canvas-game` на предыдущую сборку.
Код в Git при этом **не меняется**: следующий `git push` снова выложит
то, что лежит в `master`, поэтому ошибку в коде всё равно нужно исправить.

**Способ 2: отменить коммит через Git** (правильно для истории):

```bash
git log --oneline                    # найти хеш плохого коммита
git revert <хеш>                     # создать новый коммит, отменяющий изменения
git push                             # автодеплой выложит исправленную версию
```

Обычно делают так: сначала способ 1, чтобы сайт сразу заработал, потом
способ 2 или исправление кода.

## Словарь терминов

| Термин | Значение |
|---|---|
| Canvas | HTML-элемент, на котором JavaScript рисует пиксели |
| `ctx` | объект с командами рисования на canvas |
| Состояние | все переменные, описывающие игру в данный момент |
| Игровой цикл | функция, которая много раз в секунду обновляет состояние и рисует кадр |
| Кадр | одна картинка, нарисованная за один проход цикла |
| `dt` | время в секундах между двумя кадрами |
| Событие | сигнал от браузера: нажата клавиша, отпущена клавиша и т.п. |
| DNS | система, переводящая имя сайта в IP-адрес |
| Порт | номер, по которому ОС определяет, какому процессу отдать соединение |
| HTTP / HTTPS | протокол запросов браузера к серверу; HTTPS — зашифрованный вариант |
| Веб-сервер | процесс, который принимает HTTP-запросы и отдаёт файлы (здесь — Caddy) |
| Git | программа для хранения истории изменений файлов |
| Коммит | сохранённый снимок проекта с описанием и хешем |
| Push | отправка новых коммитов на GitHub |
| GitHub Actions | сервис GitHub, выполняющий команды на временной машине при событиях в репозитории |
| Деплой | выкладка новой версии на сервер |
| SSH | протокол защищённого подключения к удалённому компьютеру |
| Symlink | файл-ссылка, указывающий на другой файл или папку |
| Откат | возврат сайта к предыдущей версии |
